# Раздел «Аналитика» — требования

> Аналитика поверх уже построенного плана/портфеля: **реестр KPI**, **анализ узких
> мест**, **инвестпроекты** (окупаемость докупки оборудования через рынок и
> производительность) и **диаграммы потоков**. Вход — построенный план (Стадия 1) и
> портфель (Стадия 2). Ничего не пересчитывает «с нуля» — читает выходы движка.

Спроектировано по разбору аналитики **Palantir** (Foundry Ontology-metrics, Contour/
Quiver, Workshop Object Views, Vertex what-if, Gotham decision-with-ROI) и адаптировано
под то, что MAOS **уже умеет считать** (Scheduler.cpp, Optimizer.cpp, /api/simulation).

## Что даёт Palantir и что берём себе

| Возможность Palantir | В MAOS |
|---|---|
| KPI как **метрики на онтологии** (объявлены раз, переиспользуются, drill-through к объекту) | **Реестр KPI** с формулами/категориями; клик по KPI → на Схему/План |
| **Bottleneck / constraint identification** | Уже: `bottleneck{wc_type,util}`; расширяем до **ранжира top-N** + труд |
| **Resource optimization** (портфель под ограничения) | Уже: устойчивый портфель CVaR/worst-case (Optimizer) |
| **What-if / simulation-driven decision** | Сценарии + Монте-Карло; **инвест-what-if** = ре-ран оптимизатора с +N станков |
| **Decision recommendation с ROI** («сделай X → +Y, окупится за T») | **Инвестпроекты**: узкое место → докупка → выпуск → сбыт по рынку → NPV/IRR/payback |
| **Flow analytics** (Sankey, тепловые карты) | **Потоки**: Sankey тип→тип из Ганта; тепловая карта загрузки станок×время |
| **Actions log** (решение с проектной/фактической ценностью) | Аудит уже есть; инвестпроект можно «принять» (запись в реестр) |

## Вкладки раздела

### 1. KPI (реестр показателей)
Единая таблица определений (не хардкод формул в UI). Категории и показатели —
все **эмитятся движком** (ПРИОРИТЕТ 1, ~1:1 с JSON):

- **Исполнение:** Makespan, OTD (в срок), Tardiness (+CVaR), Flow time (цикл заказа).
- **Ресурсы:** Загрузка оборудования (avg), Загрузка узкого места, Загрузка по типу РЦ,
  Загрузка труда, Доля простоя, Доля ожидания в очереди, Доля наладок, Простой ТО+поломки.
- **Поток:** НЗП (WIP), Проходка (ед./дн).
- **Экономика/Риск:** Себестоимость ед., Маржинальный вклад, E[прибыль], CVaR, Худший,
  P(убыток), Цена устойчивости.

Схема реестра `kpi_registry(code, name, name_en, category, unit, direction, formula, level)`
— на первом этапе как **фронтовый каталог** (`src/features/analytics/kpiCatalog.ts`),
значения подставляются из `/api/simulation/results`, `/api/schedule`, `/api/optimize`.
Каждая карточка: значение, единица, стрелка «хорошо/плохо», формула по наведению,
клик → на связанный объект (Схема/План).

### 2. Узкие места (constraints)
Ранжир типов РЦ по загрузке — где система «упирается». По каждому:
- **загрузка** (busy/capacity), **пик очереди**, **станков vs операторов** (труд —
  из [`labor.ts`](../src/features/nsi/labor.ts): параллелизм = min(станки, операторы));
- признак **чем связан**: мощностью станков или числом операторов;
- нарратив потерь + кнопка **«Рассчитать инвестпроект →»** (переносит тип на вкладку 3).

Данные: `/api/simulation/results.per_machine` (агрегируем в загрузку по типу) + реестры
машин/рабочих. Теория ограничений: сняли первое узкое место → появляется следующее.

### 3. Инвестпроекты (флагман) — отдельная вкладка
Калькулятор: **узкое место → докупить N станков типа T → сколько даст и когда окупится.**
Считается через **рыночную модель** (сбыт ограничен ёмкостью и падает по эластичности)
и **производительность** (мощность = станки × фонд × эффективность), а не «на глаз».

**Алгоритм** (`POST /api/analytics/investment`, тело `{wc_type_id, add_machines, machine_capex, discount_rate?, scenario_id?, samples?, horizon_hours?}`):

1. **База:** ре-ран оптимизатора (dry-run, без записи в БД) → `profit0`, загрузка `util0`.
2. **С инвестицией:** ре-ран с `machineBonus[T]=+N` (мощность типа T растёт:
   `cap = (machineCount+N)·horizon·efficiency·calFactor`) → `profit1`, `util1`, новое узкое место.
3. **Прирост:** `ΔProfit = profit1 − profit0` за горизонт (уже нетто переменных затрат —
   доп. выпуск сбывается только в пределах `ёмкость − конкуренты`, цена падает по эластичности;
   произведённое сверх рынка не приносит выручки → прирост сам упирается в рынок/следующий ресурс).
4. **Денежный поток:** `months = horizon_hours/720`; `ΔCF_мес = ΔProfit/months`.
5. **CAPEX** `= N × machine_capex`. **Окупаемость** `= CAPEX / ΔCF_мес` (мес).
6. **NPV** `= −CAPEX + Σ_{t=1..H} ΔCF_мес/(1+r)^t`, `r = discount_rate/12` (ставка из сценария/НСИ).
7. **IRR** — бисекция по месячной ставке (NPV=0), годовая = `(1+irr_m)^12−1`.
8. **ROI** `= (ΔCF_мес·H − CAPEX)/CAPEX`.
9. Возврат: CAPEX, ΔProfit, ΔCF/мес, payback, NPV, IRR, ROI, `util_before/after`,
   **следующее узкое место** (куда «переедет» ограничение), доп. выпуск/сбыт.

Пояснения ТОС в UI: прирост валиден, пока T остаётся ограничением; после снятия —
ограничение переходит к следующему ресурсу (показываем его). Чувствительность/риск —
по желанию через тот же Монте-Карло (E[NPV], P(NPV<0)).

### 4. Потоки (flow analytics)
- **Sankey** тип РЦ → тип РЦ: толщина ребра ∝ числу партий, перетекающих между
  переделами (из ленты плана: последовательные операции заказа, `machine_id`→тип).
- **Тепловая карта** загрузки «станок × время» (из `per_machine`/`util_series`).

Данные из `/api/simulation/plan` (ленты задач) + реестр машин — считается на фронте,
SVG в стиле существующих (ProfitDistribution, ParetoFrontier, веер прогноза).

## Будущее (не в этой итерации)
- **Буферы с ограничением ёмкости** (blocking/starvation между переделами) — требует
  доработки симулятора (очереди сейчас неограничены).
- **План-факт** — фиксация факта выполнения (отложено по решению владельца).
- **KPI-реестр в БД** с версионностью и привязкой к уровням СТС (сейчас каталог на фронте).
- **OEE** = Availability×Performance×Quality (Quality — заглушка до модели брака).
