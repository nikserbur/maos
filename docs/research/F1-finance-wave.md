## 2. V2 — тождества водопада

### 2.1 Ручной пример §4.7 (тест `HandComputedExampleOfSection4_7`, допуск 1e-9)
Воспроизведено ровно по формуле `r_w = 1.52^{1/52} − 1 = 0.008079…` (в документе округлено до 0.36):

| t | Инкассация | Оплата поставщику | Int | d_t | C_t |
|---|---|---|---|---|---|
| 1 | 0 | 0 | 0 | 0 | 40 |
| 2 | 122 | 146.4 | 0 | 44.4 | 0 |
| 3 | 244 | 146.4 | 0.35872 | 0 | 37.2413 − 35.2 (НДС) = **2.0413** |

NOL = 20.3587, налог 0, D₃ = 44.4, AR₃ = 122, AP₃ = 0; кассовое тождество `100 + 366 − 292.8 − 180 − 0.35872 + 44.4 − 35.2 = 2.0413` ✓;
дебиторка `488 = 366 + 122` ✓; касса-минимум 0, разрыва нет ✓.
При лимите 40: в t=2 транш 40, нехватка 4.4 → **событие разрыва**, режется платёж поставщику (146.4 → 142.0), зарплата/энергия не тронуты,
просрочка 4.4 предъявляется в t=3; в t=3 при исчерпанном лимите касса снова не покрывает НДС → второй разрыв на 2.3234 (тест `LimitFortyCausesBreachAndPriorityCut`).

### 2.2 Невязки §4.6 на случайных входах (тест `IdentitiesHoldOnRandomInputs`)
300 случайных наборов (C₀, лимит, ставки, ядро DSO, предоплата, L, DPO, сетки НДС/налога, недели выплат, дефолты с LGD, овердрафт, autoRepay, транши извне, 4–33 недели).
Все семь невязок ≤ **1e-9·масштаб** (масштаб = C₀ + лимит + Σ выручка + Σ закупки + Σ capex):
1 касса (по всем t), 2 сверка прибыли и денег `Σ Π^acc = Σ CF^op − Σ Dep + ΔWC_ext`, 3 дебиторка (`AR_H + Σ Coll + Σ списания = Σ Rev(1+τ_v)` и независимый пересчёт остатка по ядру),
4 долг и проценты, 5 разложение NPV собственника с членом удержания остатка `Σ C_t (DF_{t+1} − DF_t)`, 7 материальный баланс (сырьё / в пути / ГП).
Ветви покрыты: разрывы > 0, дефолты > 0; инварианты: касса ≥ 0 без события, долг ≤ лимит, овердрафт ≤ лимит, `разрыв ⇔ чистая касса < 0`.
На демо-БД (64 изделия, N = 300, 8 периодов, масштаб ≈ 3·10⁸ ₽): `identities_max_residual = 0.0` (в более раннем прогоне 3.6·10⁻⁷ при масштабе 3·10⁸, т. е. ≈ 10⁻¹⁵ относительно).

Раскрытые упрощения (статус [НОРМ-упрощение], в шапке `CashWaterfall.h`): запасы по материальной себестоимости, конверсия — OPEX периода;
входящий НДС — в периоде счёта (= заказа); налог на прибыль — в конце налогового периода; ковенант DSCR проверяется по горизонту
(`Σ CFADS / Σ (Int + PR)`), недельный DSCR остаётся для диагностики; разрыв не удаляет путь из выборки.

## 5. R4 и R20

- **R4.** `hours_per_unit` умножает PERT-среднее на `u_o = 1 + w·(1 − 9^{1−ξ})/(ξ − 1) + 0.5·risk` — точное ожидание модели `sample_dur` Стадии 1 (логнормаль с E = mean, Парето-множитель `1 + min(8, F − 1)` с вероятностью w, переделка `+0.5·mean` с вероятностью risk). При w = 0.08, ξ = 2.5, risk = 0.05: **u = 1.07642** (тест `R4_Stage2CapacityCarriesTailAndReworkUplift`, 1e-9). Статус — [К] (паспорт `fin.stage2_tail_uplift`); выключается `tail_uplift=false` (ответ содержит флаг `tail_uplift`).
- **R20.** `POST /api/simulation/calibrate` → `409 {"error": "Калибровка заблокирована (R20): нет источника план-факта (plan_fact_ops пуста)…"}`; `GET /api/simulation/calibration` (предпросмотр) не тронут. Таблица `plan_fact_ops(operation_id, machine_id, planned_min, actual_min, qty, …, synthetic)` создана пустой под будущий `POST /api/planfact/import`.

## 7. Что не сделано (точные TODO)

1. **Стохастический спрос E[min(q, D)] (Р6, §2.4/§5.2а)** — не реализован; сейчас спрос — детерминированная граница `x_s ≤ demand_max` и насыщение через множитель цены (как в `ExactCvar`). Формула для `CashLp`: продажи в периоде `y_{i,s,t} = min(x_s φ_{s,t}, D_{i,s,t})`; по сценариям `E[min(q, D)] = (1/N) Σ_i min(q, D_i)` — вогнутая кусочно-линейная по q с изломами в порядковых статистиках `D_(1) ≤ … ≤ D_(N)` и наклонами `(N − k)/N` на `[D_(k), D_(k+1)]`; для LP достаточно ≤ ⌈log₂ N⌉ отрезков на (s, t) через квантильные бины (newsvendor-LP, §5.2а). Поскольку произведение `g_s(x)·E[min]` не вогнуто, множитель цены брать при ожидаемом заполнении (как сейчас), а потолок спроса — PWL по `x_s φ_{s,t}`; розыгрыш `D_{i,s,t}` — отдельный поток CRN `[seed, 102]` с pass-through макро по §2.4 (волна M). Это закрывает R12.
2. **Макро-пути** `i_t, S_t, π_t, τ_t, ℓ_t` — пока константы `fin_params.key_rate` (+ спред); `PeriodInput.keyRate` и `CashLp::rate[i][t]` уже принимают путь по сценарию — волна M подставит `MacroSampler`.
3. **События Стадии 1 в водопад** (`Q_{s,t}, M_{j,t}, H_{w,t}, R_{w,t}`) — профиль отгрузок берётся из `plan_tasks` (`schedule_ref_id`), но часы/энергия/ремонты по отказам в `PeriodInput` не передаются (F_t из `fin_params`, `repairBreakdown = 0`); нужен экспорт потока событий из `run_schedule` (§11.4).
4. **Зазор SAA (Мак–Мортон–Вуд, M = 10)** и график SE(N) — не считались (есть OOS на свежем seed и ДИ по N ∈ {100, 300}).
5. **`run_manifest`** (sha256 БД/паспорта, версии) и `cash_runs` — не созданы; `optimization_runs.feedback_hash` — первый шаг.
6. **`POST /api/finance/waterfall`** как отдельный эндпоинт и ЧДД инвестиций через водопад (`/api/analytics/investment`) — не сделаны; водопад вызывается только внутри `/api/optimize/cash`.
7. Входящий НДС в LP — без зачёта отрицательного сальдо вперёд (линейно); в водопаде зачёт есть. Округление LP до партий в `CashLp` — только вниз (без жадного добора `ExactCvar`).
8. UI (категория «Деньги» в `kpiCatalog.ts`, экран паспорта) — волна G; в `src/lib/api.ts` добавлены только типы и методы.

## 8. Границы результата
CVaR/CFaR условны на параметрический генератор цен v0.63 (не на обученный макро-генератор) и на калибровочные [К] параметры денег; «цена ликвидности» измерена на демо-инстансе
с равномерным профилем отгрузок и константной ставкой; все выводы — сценарные, не причинные; данные предприятия не использовались.
