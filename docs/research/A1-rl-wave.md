## 2. Среда как построена (спецификация)

### 2.1 Экземпляр и сценарий
`Instance` = `Model` НСИ (типы РЦ, станки, изделия, операции с допустимыми типами и входами, рабочие и матрица допусков, графики) + программа (`OrderSpec`: изделие, объём, срок, release, приоритет, цена, материальная себестоимость по BOM) + календари + альтернативные техкарты (`routings.is_default=0`) + параметры аутсорсинга [К] + `fin_params`. Из БД — `instance_from_db` (та же `load_model`, что в `run_schedule`); из JSON — бенчмарки и стенд (`POST /api/rl/instance` отдаёт тот же формат).

`Scenario` i: недельные пути ключевой ставки/курса/инфляции и режим HMM (из `MacroSampler`/`rl.macro`, потоки `[seed, 871/872]`), неделя дефолта покупателя (поток `[seed, 911]`, PD = `fin.pd`), множители стресса (`lead_mul`, `price_mul`). Длительности и поломки — внутри среды, **по идентичности джобы** (заказ, операция, изделие, партия k/N; splitmix64 от `seed`), а не по индексу: структурный ход одного заказа не меняет розыгрыши других (тест `ConservationAndCrnByIdentity`).

### 2.2 Моменты решения, действия, маски
| Уровень | Эпоха | Действие | Жёсткая маска (по построению) |
|---|---|---|---|
| L0 (диспетчер типа РЦ, одна политика на все типы, mean-field) | станок освободился (событие `MACHINE`; при равных временах сначала `JOB_DONE`, затем `WEEK`, затем `MACHINE`) | слот кандидата 0..15 или **WAIT** (16) | кандидат = все предшественники завершены **к моменту события** (материальный баланс и предшествование), тип станка ∈ `wcTypes` операции, станок свободен (ремонт/ТО — внутри занятости `sim_place`), есть допущенный рабочий, освобождающийся не позже события (иначе опрос в момент его освобождения), календарь станка открыт (иначе опрос в `nextWork`), запуск заказа наступил (иначе опрос в дату запуска); WAIT — только если ожидается ещё завершение операции; после WAIT станок опрашивается на ближайшем завершении |
| L2 (планировщик) | граница недели t = 0..26 (до событий недели) | один ход из меню или `noop`; до `rl.max_moves_per_week` = 3 ходов за эпоху | только **не начатые** заказы; `shift ±1 нед` (запуск + цикл по средним ≤ срок; сдвиг ≤ 4 нед; не раньше `release_hours`); `split`/`merge` (N′ ∈ [1, 16], N′ ≤ объём/партия — по умолчанию партии уже по `batch_size`, поэтому `split` допустим только после `merge`); `outsource` (есть предложение [К], есть полуфабрикат с техкартой во входах, C_t + U_t ≥ предоплата); `reroute` (есть `is_default=0`); `reassign` (у операции > 1 допустимого типа и есть станки альтернативы); `finance`: транш 25/50/100 % невыбранного лимита (d_t ≤ U_t), погашение 50/100 % (C_t − C_min, при долге) |
| Serial (эталон) | каждое размещение | джоба из полного списка готовых | как `simulate()`; политика «argmin ключа» воспроизводит `run_schedule` **побитово** для EDD/SPT/LPT/CR/MWKR/MS/FIFO (тест) |

Ходы «отказ от заказа», «перенос цеха», «условия покупателя/поставщика» — волна 2 (Р5), в среде не реализованы.

### 2.3 Наблюдения (фиксированной размерности, для ONNX)
- **L0** (206 = 16 × 12 + 4 + 4 + 6): на слот — ожидаемая длительность на этом типе / масштаб, σ/μ, запас по сроку (срок − t − остаток цепочки), флаг наладки (смена изделия на станке), число входов, остаток цепочки, стоимость заказа (доля от максимальной), доля выполненных операций заказа, «последняя операция», k/N партии, время ожидания в очереди, приоритет; станок — наработка до ТО, загрузка, ход времени, доля простоя; пул соседей по типу — доля свободных, средняя остаточная занятость, доля настроенных на изделие первого кандидата, число соседей; глобально — режим HMM (one-hot 3), флаг «касса в зоне риска», ключевая ставка, доля выполненных джоб. Слоты заполняются в EDD-порядке; очередь длиннее 16 усекается (**[К] `rl.k_max_cands`**; ограничение раскрыто).
- **L2** (172 = 16 × 8 + 32 + 12): на заказ — запас по сроку, остаток работы, стоимость, начат ли, N партий, сдвиг, число аутсорсингов, флаг «уже не успевает»; очередь готовых операций по 32 типам РЦ; касса/долг/невыбранный лимит (нормированы), флаг разрыва, DSCR, ставка, курс, инфляция, режим, неделя. Касса на неделю t — прогон водопада по неделям [0, t) (дёшево: ≤ 26 периодов).

### 2.4 Награда
- L0, плотная (L2D-типа): −Δ нижней оценки Cmax (оценка по предшествованию и средним с учётом фактических окончаний) − c_T·Δ оценки суммарной просрочки − c_S·наладка; всё в долях начальной оценки Cmax. Энергия — 0 (кВт·ч по типам в НСИ нет, `rl.reward.c_energy`).
- Терминальная (кооперативная, обоим уровням): w_Π·Π/|V| + w_C·min(0, C_min)/|V| − λ·1[разрыв] − ½λ·1[ковенант], V = стоимость портфеля; Π и C_min — из недельного водопада `cash::run` на **фиксированном** горизонте (26 недель, округлённом до границы налогового периода — 28): выручка заказов, завершённых позже, в эпизод не входит. (Первая версия тянула горизонт за makespan — и «позже = меньше налога в последнем неполном периоде» давало +30 % прибыли за сдвиг запуска; артефакт найден проверкой ходов и устранён.)
- Бухгалтерия недели: заказ сырья `orders` на неделе запуска − L (в `book_order_start`), списание в производство, конверсионные затраты и зарплата по завершённым операциям (ставки типа/операции), ремонт = часы отказа × ставка типа × `rl.repair_cost_mul`, выручка и COGS на неделе завершения заказа, договорной штраф `rl.tard_penalty_per_week` (1 %/нед, потолок 20 %) — в прочие платежи; ключевая ставка недели из макро-пути; транши L2 → `drawdown`/`repayment` водопада (иначе правило §4.3 п.8).
- CVaR-перевзвешивание эпизодов по пакету CRN (Tamar 2015) — на стенде при оценке, не внутри среды; обучение PPO идёт на средней награде (ограничение, см. §7).

### 2.5 Производительность
Полный демо-портфель (34 заказа, 2 808 джоб, 120 станков): эпизод по правилу ≈ 90 мс (C++); ~2 800 решений L0. Обучение MaskablePPO через nanobind: ≈ 250–400 шагов/с на один процесс (узкое место — Python/torch, не среда).

## 3. V4 — расписание: правила / ГА / CP-SAT против BKS и LB

Протокол: детерминированно (средние длительности, без поломок), серийное списочное планирование по ключу правила (= `run_schedule`), событийный non-delay режим SimEnv, ГА по ключам (хромосома GaImprover: 5 весов критериев + сдвиг заказа; затравки — все правила; 30 поколений / 30 с), CP-SAT (OR-Tools 9.15, 8 потоков, 60 с [НОРМ]; интервальная модель с альтернативными станками, NoOverlap, предшествование). LB = max(самая длинная цепочка по минимальным временам, max по станку Σ работ с единственной альтернативой). На экземплярах MAOS CP-SAT — **релаксация** (без наладок, рабочих и календарей; детерминированная часть считается без календарей 24×7, чтобы сравнение было сопоставимым), поэтому «разрыв к CP-SAT» там — разрыв к нижней границе, не к оптимуму.

- Серийная схема с правилами на бенчмарках без сроков вырождается (все due равны → EDD/CR/MS ≈ FIFO): +41…66 % к BKS; событийный non-delay режим той же среды даёт +12…25 % на Taillard и на mk03/mk08 **совпадает с оптимумом** — подтверждение A4 §3: «серийная vs событийная» разница — находка сама по себе, и именно событийный режим является честной базой для L0.
- ГА по ключам сокращает разрыв правил примерно вдвое (+20…30 % на Taillard), но остаётся далеко от CP-SAT: на детерминированной задаче размера цеха точный солвер выигрывает (A4 §0, Tassel 2023) — RL здесь не оправдан, что и постулирует §7.1.
- На экземплярах MAOS разрыв правил к релаксации 130–185 % — в основном из-за наладок/рабочих/лотов, которых релаксация не видит; это верхняя оценка «цены структуры», а не неэффективность правил.

**Что подтвердилось / что нет (формат B2):**
- RL **не** выиграл: все L0 статистически значимо хуже лучшего правила и ГА по CVaR₀.₁(Π) (ДИ целиком < 0, p ≈ 0,03), проигрыш по E[Cmax] +70…+146 ч; L2+EDD неотличима от EDD (ДИ содержат 0, |Δ| < 0,04 %). Гейт §7.4 не пройден ни одной политикой; чемпион = `best_rule`; `rl/results/champion.json`. В стрессах выводы те же — выигрыша в кризисе/квантилях/совместном шоке нет.
- ГА ≈ лучшее правило по деньгам (ΔCVaR −0,004 %, ДИ [−0,01; −0,00] %, p = 0,05 — формально значимо хуже на ничтожную величину) при −3,6 ч E[Cmax]: **прибыль на 26-недельном горизонте почти нечувствительна к качеству расписания**, если все заказы укладываются в сроки (OTD = 1 у правил). На демо-экземплярах разброс целевой функции между политиками 0,01–0,1 % E[Π] — на порядок меньше эффекта макро-стресса (joint: −37 %). Это главный содержательный вывод V5: структурный RL имеет смысл там, где сроки/мощность напряжены (OTD < 1) и есть альтернативы в НСИ; на текущих демо-данных задача для него «не стоит».
- Критерий L0 — плотная награда по Cmax — политикой не выучен (WAIT-тяжёлая); это ограничение бюджета обучения и MLP-архитектуры, а не среды: правила в той же среде ведут себя как ожидается (V4), тесты эквивалентности проходят.


## 6. Правило «RL» в продукте (что сделано и как работает)

- Путь выбран **ONNX + C++ (onnxruntime 1.20.1, prebuilt, FetchContent с SHA256)**, не Python-эндпоинт: `rule:"RL"` в `POST /api/schedule` → `rl::plan` прогоняет политику L0 в событийной SimEnv по средним длительностям и отдаёт **ключ приоритетов (ранг старта)**; дальше работает неизменённый конвейер (Ганта, МК по CRN, ГА при `improve_iters>0`); ответ содержит `rl: {makespan_h, tardiness_h, n_decisions, n_wait, policy_sha256}` и `moves: MovesResult | null`. Путь EDD/SPT/… не тронут (тест `WithoutPolicyRuleRlIsSoftErrorAndEddUntouched`).
- `moves[]` (контракт UX-V2 §4.7): ходы L2 по средним; `impact` — «до/после» пакета на N = min(60, max(20, samples/10)) сценариях CRN (E и CVaR_α прибыли, CVaR_0.05 min-кассы, P(разрыв), ΔCmax/OTD/просрочка, доля выигрышных сценариев, бутстреп-ДИ); `justification` — топ-5 сценариев по выигрышу, узлы карты [6]→[4]→[5], текст; `guardrails.allowed` отражает НСИ (нет альтернативных техкарт → `reroute=false`). Атрибуция — на пакет, не на отдельный ход (так и подписано в `text`).
- Проверено через API с кандидатами seed 1: `rule:"RL"` на 4 заказах → Ганта за 8 с с `moves` (L2 предложил 0 ходов), `GET /api/rl/status` отдаёт SHA256 обеих политик; без файлов политики — `error_soft` с причиной.
- **По гейту §7.4 ни одна политика не стала чемпионом**, поэтому `rl/results/l0_policy.onnx` **не публикуется**: сервер по умолчанию отвечает «правило RL недоступно». Кандидаты лежат как `rl/results/l0_policy_seed{1,2,3}.onnx`, `l2_policy_seed{1,2,3}.onnx` (+ `.json` с SHA256, размерами и командой регенерации; `rl.policy_version`); включить любой можно, положив его как `l0_policy.onnx` в `$MAOS_RL_POLICY_DIR` — это осознанное действие, а не состояние по умолчанию.
- `src/lib/api.ts`: типы `StructuralMove`, `MoveImpact`, `MoveJustification`, `AgentGuardrails`, `MovesResult`, `RlStatus`, `RlEval`, `ScheduleResult.moves/rl`, `api.rl.status/instance`. `src/features/*` не трогались.

## 7. Ограничения, честные оговорки и что остаётся

**Ограничения построенного:**
- Очередь кандидатов L0 усекается до 16 слотов в EDD-порядке; политика — MLP, без внимания над множеством (A4 §3 рекомендует внимание для ONNX).
- CVaR-перевзвешивание эпизодов (Tamar 2015) в обучении не применено — PPO на средней награде; CVaR — только в оценке.
- Энергия в награде = 0 (нет кВт·ч по типам); ремонт оценивается по ставке типа [К]; штраф за просрочку [К] 1 %/нед (договоров нет); аутсорсинг — единое предложение [К] (72 ч, ×1,3).
- Ходы `reroute/reassign/outsource` реализованы и покрыты тестами на синтетическом экземпляре, но на демо-НСИ всегда маскированы (нет данных) — отчёт V5 про «какие ходы использованы» этим ограничен.
- CP-SAT на экземплярах MAOS — релаксация (без наладок, рабочих, календарей) → нижняя граница, не оптимум; на бенчмарках — честный эталон.
- Обучение шло на одном ноутбуке параллельно с бенчмарками: 200k шагов на сид — на 1–2 порядка меньше, чем в литературе; стадия 4 куррикулума (совместное обучение L0+L2) не выполнена, L2 обучена поверх EDD.
- Оценка «WAIT-тяжёлых» политик дорогая (десятки тысяч эпох на эпизод), поэтому валидация — 4 сценария на экземпляр; holdout — 200 по протоколу.
- В `RlRule` макро-путь не подключён: `moves.impact` считается при ставке из `fin_params` (режим «base»), стрессы — только на стенде.

**Что остаётся (в порядке ценности):**
1. Дообучение L0 до 2–5 млн решений с вниманием над множеством кандидатов (RL4CO/L2D-архитектура), затем экспорт; PBT по c_T/c_S/c_W. Без этого правило RL в продукте остаётся выключенным гейтом.
2. Совместное обучение L0+L2 (стадия 4) и CVaR-перевзвешивание по пакету CRN.
3. НСИ для структурных ходов: альтернативные техкарты (`is_default=0` для ≥ 30 % изделий), `outsourcing_offers`, второй допустимый тип у операций — иначе V5 «структурный» по определению пуст.
4. `POST /api/runs/:id/moves/decide` (принять/отклонить/заморозить → новый прогон) и подключение макро-пути в `RlRule`.
5. Volna «Игры» (V6) — PoA/Штакельберг — не начата.
