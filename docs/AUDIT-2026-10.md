## 1. Сводка аудита

### 1.1 Дизайн и UX (A1)
- **Критично:** один и тот же KPI вычисляется по-разному на разных экранах —
  «Проходка» (ед./сут в Плане vs заказы/сут в симуляции vs «партий» в каталоге),
  «Загрузка» (календарный фонд vs 24/7), «Makespan» (MC-среднее vs детерминированное),
  подпись «Концентрация (HHI)» у максимальной доли. **До слоя «i» это надо унифицировать** (§4.2).
- Дизайн-система не выдержит редизайн: 30 токенов, нет шкал типографики/отступов/теней/движения;
  **767 захардкоженных цветов**, 300 inline-стилей, 20 размеров шрифта, 19 радиусов,
  два «диалекта» (2–3 px Blueprint и мягкие 6–12 px). `--surface*`, `--danger` не определены →
  **светлая тема сломана на 4 экранах**.
- IA: рейл из иконок без подписей, порядок не совпадает с потоком данных
  (Стадия 1 стоит перед Стадией 2), нет URL-маршрутизации, результаты Плана/Оптимизации теряются при переключении.
- Моделирование размазано по трём несвязанным метафорам (3D, формы, линейный IDEF0);
  **связи на 3D-схеме не читаются движком**; две BOM; IDEF0 сохраняет t_opt = t_norm = t_pess
  (σ «хвоста» молча = 15 %); переименование цеха/завода шлёт `machines.update` (`PlantScene.tsx:180-183`).
- Объяснения есть, но спрятаны: 56 нативных `title=`, формулы только в Аналитике,
  методика прогноза скрыта во встроенном режиме. 55 «проглоченных» ошибок выглядят как пустые данные.

### 1.2 Методика (A2)
Инженерия добротная (CRN, out-of-sample SAA, эмпирический CVaR, корректная копула, backtest против наивного прогноза),
но как научный вклад диплома слабее в четырёх местах:
1. **Стадия 2 решается эвристикой** (~120 кандидатов + tie-break по равномерности), хотя задача
   CVaR с ёмкостными ограничениями решается **точно** как LP/QP (Rockafellar–Uryasev 2000/2002).
2. Заявление «двухэтапная стохастическая задача с рекурсом» **неверно**: сценарных решений второго этапа нет →
   корректно «**иерархическая двухуровневая модель планирования**».
3. Нет тестов, бенчмарков (Taillard, Brandimarte, CP-SAT), доверительных интервалов, анализа чувствительности.
4. **17 подтверждённых багов** (Scheduler/Optimizer/main/kpiCatalog), из них меняют результат:
   B1 (lot-streaming: потребитель стартует раньше входов), B3 (снабжение занимает рабочего на весь lead time),
   B4 (24×7 падает на сменный календарь), B5 (риск-KPI от расписания до локального поиска),
   B6 (NPV по номинальной r/12, IRR — эффективная), B7 (калибровка циклична), B8–B10 (KPI-формулы/единицы),
   B14 (MRP-смещение на единицу вместо партии), B16 («следующее узкое место»).
5. Коэффициенты макрофакторов подобраны «для заметного эффекта ползунков» (`main.cpp:2294`) — ненаучно.

### 1.3 Palantir и конкуренты (A3)
- **Palantir** моделирует завод как объекты/связи Ontology, все записи — через управляемые **Actions**
  (валидация, права, аудит); сценарий = изолированный форк из дельт, сравнение и merge через Action;
  **Gantt-контракт** suggest → search → validate → review → commit; ИИ-агенты (AIP) никогда не пишут
  напрямую — только предлагают Actions, человек подтверждает, качество меряют Evals.
  **Встроенного оптимизатора нет** (BYO-модели), нет первоклассного «объясни формулу KPI», визуальный язык — 2D-графы.
- Рынок: Siemens Opcenter APS (GA/MCTS), Kinaxis (250k сценариев/мес, cuOpt), o9/Cognite (графы знаний + агенты),
  Tulip (агенты перепланирования), **Seeq — эталон прозрачности формул**. «Вероятностное» планирование у лидеров
  во многом маркетинг; Simio RPS лишь *оценивает* риск после планирования. Россия: рынок APS ₽591 млн (2025), лидеров нет,
  планирование в Excel, западные вендоры ушли, дедлайн импортозамещения КИИ 2030.
- **Отличия MAOS:** стохастическая/робастная оптимизация совмещена с расписанием; реестр формул KPI;
  NPV/IRR через теорию ограничений; 3D-схема = система записи; офлайн, суверенно (SQLite).
- **Пробелы MAOS (по приоритету):** Action layer + аудит → форк/merge сценариев → drill-down KPI до строк →
  валидация и подсказки на Ганте → inbox предложений агентов + evals → импорт/маппинг (1С/Excel) → RL.
- **Позиционирование:** «**прозрачный (glass-box) стохастический APS-двойник**» — APS-контур к 1С:ERP
  для среднего дискретного производства РФ.

### 1.4 Агентный слой / RL для одного завода (A4)
- Макро-программа друга переносится на завод чисто: агенты = диспетчеры станков (общая политика на тип РЦ),
  «секторы» = начальники цехов, «регулятор» = **планировщик завода**, задающий внутренние трансфертные цены
  машино-часа и бонусы заказов (как AI Economist); «система уравнений и балансов» = дискретно-событийный симулятор MAOS;
  «common noise» = общезаводские шоки (уже есть фактор рынка `M`).
- **Материальный баланс** — через симулятор и маскирование недопустимых действий, а не PINN-штрафы; PINN/KKT-проекция
  уместны только в обучаемых суррогатах. Mean-field при K≈1–10 станков на тип = разделение параметров + пул состояния;
  научная метрика — **цена анархии** (MFG vs MFC): сколько теряет система KPI/бонусов цехов.
- **Скрытые неэффективности:** сравнение выученных цен планировщика с **двойственными ценами LP** Стадии 2 →
  «фантомные узкие места» (переналадки/синхронизация BOM, а не мощность); каждую находку подтверждать A/B в симуляторе (CRN).
- **Поправка к ссылкам друга:** рабочая записка Банка Англии (WP 1142, 2025) обучает RL-**домохозяйства**,
  а не RL-центробанк; переносимы лишь предупреждения (медленное нестабильное обучение, множественность равновесий).
- **Ключевой рефакторинг:** нынешний `simulate()` — последовательная схема (операции размещаются не по времени),
  «состояние завода в момент t» не определено → нужен **событийный `SimEnv`** рядом с ним, pybind11/nanobind,
  обученная политика возвращается в C++ через ONNX Runtime как правило «RL».
- **Где RL не нужен:** статическое детерминированное расписание (CP-SAT лучше) и портфель Стадии 2 (точный CVaR-LP).
  Где нужен: оперативная перепланировка при тяжёлых хвостах, поломках и шоках; исследование стимулов.

### 1.5 Стек и практики (A5)
- Бюджет JS уже превышен (~330 KB gzip при ~300 KB): **визуальные эффекты — без новых зависимостей**
  (OKLCH + `color-mix()`, aurora на transform, зерно SVG `feTurbulence`), всё новое — ленивой загрузкой по экранам.
- `@react-three/postprocessing` 3.x требует React 19 + R3F 9 → новые 3D-зависимости не добавляем до миграции.
- Подсказки «i»: реестр метрик + поповер на `@floating-ui/react-dom` (9 KB). Граф процесса: собственный холст
  (движок уже есть в AI-воркфлоу) без tldraw/elkjs. RL-стек: nanobind/pybind11 → PettingZoo → MaskablePPO → MAPPO (TorchRL), ONNX Runtime C++.

### 1.6 Визуальное направление (A6)
«**Конструктивный Кандинский**»: плотность Blueprint сохраняется; вместо плоского холодного серого —
тёмный фон с ультрамариновым оттенком и тёплый «костяной» текст; акценты — ультрамарин / охра / киноварь,
плюс ярь-медянка и бычья кровь. Один геометрический словарь (точка, линия, ●, ■, ▲) для логотипа, статусов и схем.
Атмосфера (aurora, зерно, ореол) — только в «хроме» и пустых состояниях, **никогда** на таблицах, Ганте, KPI, 3D и карте.
Шрифты: **Onest** (UI), **Unbounded** (заголовки), **JetBrains Mono** (код/ID) — self-host.
Логотипы: №3 «Терпкий» — favicon/иконка, №1 «Триада» — в верхней панели и локапе, №2 «Несколько кругов» — герой окна входа.

## 2. Принципы решений

1. **Прозрачность как бренд**: каждое вычисляемое число имеет «i» — формула, подстановка живых значений, единицы, метод, оговорки, схема, ссылка в «Методику».
2. **Сначала правильность, потом красота**: унифицировать определения KPI и исправить баги P0 до того, как подсказки начнут их документировать.
3. **Ноль новых runtime-зависимостей для визуала**; новые экраны — ленивые.
4. **Атмосфера не мешает данным**: эффекты только в хроме/логине/пустых состояниях, `prefers-reduced-motion`, пауза aurora при видимой 3D/карте, без `backdrop-filter` над WebGL.
5. **Цвет никогда не единственный сигнал**: статусы = цвет + глиф (● ▲ ○ ■).
6. **Научная корректность терминов** (ГОСТ Р ИСО 22400-2-2019, ГОСТ 27.002-2015, ВК 477, ГОСТ Р 57700.37-2021).
7. **Хирургические правки**: каждый агент трогает только свои файлы (§6); версию и коммиты не трогаем без запроса.

### Волна 3 — агентный слой RL (≈8–12 недель, глава диплома)
