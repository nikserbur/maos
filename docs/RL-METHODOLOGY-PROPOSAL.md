# Агентный слой MAOS (RL/MARL) — предложение методологии на согласование

> Статус: **СОГЛАСОВАНО 2026-10-19** (решения — §8). Основа — исследование
> [A4](research/A4-rl-plant-science.md) (~45 проверенных ссылок) и аудит методики [A2](research/A2-methodology-audit.md).

## 1. Идея в одном абзаце
Макро-программа «агенты-предприятия обучаются внутри заданной системы уравнений и балансов, а над ними
обучается регулятор» переносится на **один завод**: агенты — диспетчеры станков и начальники цехов,
«регулятор» — **планировщик завода**, который задаёт внутренние цены машино-часа и бонусы заказам;
«система уравнений и балансов» — дискретно-событийный симулятор MAOS (материальный баланс, мощности,
календари, поломки, тяжёлые хвосты длительностей). Цель — не «заменить оптимизатор нейросетью», а
(1) научиться **оперативно перепланировать** под неопределённостью лучше правил и (2) **измерить, сколько
теряет завод из-за системы KPI/стимулов цехов**, и найти скрытые неэффективности.

## 2. Границы (что RL НЕ делает)
- Статическое детерминированное расписание размером с завод лучше решает точный CP-SAT — он будет эталоном.
- Портфель Стадии 2 решается точно CVaR-LP (Rockafellar–Uryasev) — RL туда не нужен.
- **ТЭБ исключён**: энергия — только экзогенная статья затрат (тариф × машино-часы), без моделирования баланса.

## 3. Как это будет работать
```
 БД проекта ──экспорт──► инстанс (заказы, маршруты, BOM, календари, параметры шоков)
                              │
            ┌─────────────────▼──────────────────┐
            │ SimEnv (C++, событийный, рядом с    │  reset(seed) / step(действие) / маска / наблюдение
            │ нынешним Scheduler)                 │  — материальный баланс соблюдается ПО ПОСТРОЕНИЮ
            └───────┬─────────────────────────────┘
      nanobind (в процессе, микросекунды)
            │
 Python-стенд rl/ (вне продукта): Gymnasium / PettingZoo → MaskablePPO → MAPPO (TorchRL/BenchMARL)
            │  экспорт политики torch → ONNX
            ▼
 ONNX Runtime в C++: новое правило «RL» рядом с EDD/SPT/… → Гант, KPI, сравнение правил в UI
```
**Агенты (3 уровня, вводятся поэтапно):**
| Уровень | Агент | Когда решает | Действие | Награда |
|---|---|---|---|---|
| L0 | диспетчер станка (одна политика на тип РЦ — «mean-field») | станок освободился | какую операцию из очереди взять (или ждать) | вклад в длину расписания, просрочку, переналадки |
| L1 | начальник цеха | смена | веса правил, лимит НЗП, сверхурочные | KPI цеха (по внутренним ценам) |
| L2 | планировщик завода | сутки/период | цены машино-часа по типам РЦ, бонусы заказам, график запуска | CVaR прибыли завода по сценариям |

**Ограничения:** жёсткие (наличие входов, предшествование, один станок — одна операция, допуск рабочего,
календарь) — **маскированием действий**; мягкие (НЗП, энергия, CVaR просрочки) — **PID-лагранжиан**, множители
читаются как «цены ограничений». PINN-подобные слои — только в обучаемом суррогате для планировщика L2.

**Общий шум (common noise):** шоки спроса и сроков, рыночный режим M(t) (процесс Орнштейна–Уленбека со скачками —
стохастика друга), задержки поставок, тарифные пики, невыходы. Сценарии одинаковы для всех сравниваемых
политик (CRN).

## 4. Что считается научным результатом
1. **Робастная диспетчеризация** при тяжёлых хвостах и общих шоках: выигрыш RL над лучшим правилом с 95% ДИ.
2. **Цена анархии** системы KPI цехов: J(игра цехов) / J(кооперативное управление) — сколько теряет завод из-за стимулов.
3. **Фантомные узкие места**: выученные цены планировщика против двойственных цен LP Стадии 2 — высокая цена при
   средней загрузке = потери от переналадок/синхронизации, а не от мощности; каждая находка подтверждается A/B в симуляторе.
4. **Гейтированное самоулучшение**: новая политика заменяет старую, только если выигрывает значимо на отложенных сидах.

**Доказательность:** базовые линии (7 правил, ATC, текущий поиск, **генетический алгоритм по ключам приоритетов**, CP-SAT),
бенчмарки Taillard/Brandimarte + инстансы MAOS, ≥5 сидов обучения × ≥200 сценариев оценки, IQM + bootstrap-ДИ, тест Уилкоксона.

## 5. Этапы
| Этап | Срок | Результат |
|---|---|---|
| Ф0 | ~4 дня | событийный SimEnv + маски + тесты эквивалентности, nanobind, Gymnasium, базовые линии |
| Ф1 | ~1 нед | политика выбирает правило по типу РЦ (MaskablePPO) — первый честный выигрыш/проигрыш с ДИ |
| Ф2 | ~1 нед | прямой диспетчер (внимание), бенчмарки, ONNX → правило «RL» в UI |
| Ф3 | 3–4 нед | MARL станков (MAPPO, mean-field пул), лагранжиан ограничений, общие шоки |
| Ф4 | 3–4 нед | планировщик цен/бонусов (куррикулум AI Economist), цены vs LP-двойственные, цена анархии |
| Ф5 | 2–3 нед | самоулучшение (self-labelling + PBT), кейсы неэффективностей, глава диплома |

## 7. Решения на согласование
1. С какого уровня агентов начинаем (рекомендация: L0 → потом L2).
2. Какая цель главная: кооперативная (CVaR завода) или исследование стимулов цехов (рекомендация: обе, кооперативная — базовая).
3. Python-стенд `rl/` в репозитории + ONNX Runtime как новая зависимость C++-бэкенда — допустимо?
4. Где RL живёт в продукте: новое правило Стадии 1 / онлайн-перепланировка в симуляции / только исследовательский стенд.
5. ГА по ключам приоритетов как базовая линия и замена слабого hill-climb в Стадии 1 (связка с заставкой) — делать?

## 8. Принятые решения (согласовано 2026-10-19)
| # | Вопрос | Решение |
|---|---|---|
| 1 | Уровни агентов | **Сразу двухуровневая система L0 + L2**: диспетчеры станков (политика на тип РЦ) и планировщик завода (цены машино-часа, бонусы заказам). L1 (цеха) — позже. Риски нестабильности двухуровневого обучения закрываем куррикулумом AI Economist (сначала L0 без планировщика, затем совместное обучение с отжигом энтропии), ранней остановкой и отчётом по нескольким равновесиям/сидам. |
| 2 | Цель | **Обе, кооперативная — базовая**: CVaR прибыли/сроков завода; исследование стимулов (цена анархии) — отдельная глава. |
| 3 | Место в продукте | **Правило «RL» в Стадии 1**: политика ONNX рядом с EDD/SPT, сравнение в UI с доверительными интервалами. |
| 4 | Инфраструктура | Одобрено: **Python-стенд `rl/`** в репозитории (PyTorch, Gymnasium/PettingZoo, BenchMARL; nanobind к C++), **ONNX Runtime** в бэкенде, **ГА в Стадии 1** (базовая линия + замена hill-climb), **бенчмарки Taillard/Brandimarte + CP-SAT** (OR-Tools в Python-стенде). |

**Порядок реализации:** ГА в Стадии 1 → Ф0 (SimEnv + nanobind + стенд + базовые линии/CP-SAT/бенчмарки) →
Ф1–Ф2 (L0) → Ф4 (L2 поверх обученного L0, затем совместно) → ONNX-правило «RL» в UI → Ф5.
